This report describes a prototype that was built and measured on 2026-09-09. Its purpose is narrow and worth stating first: to prove that a request typed into a browser, or issued from Claude Code, can travel through an agent harness and end as a real analysis job running on the compute cluster — with every hop verified rather than assumed. It is not the finished OMAKASE system; what it deliberately is not is set out in section 8. Section 7 is different in kind from the rest of this report: it describes the use case agreed in a meeting on 2026-09-10, none of which is implemented, and it names the two questions that have to be answered before that work can be planned.

1What the chain is

Five components sit between a human and a compute job today. Each existed for its own reasons before this prototype; the work of 2026-09-09 was to make them one path and to measure it. The figure also shows, in grey and amber, the parts of the intended system that are not part of that measurement, so that the picture is of the system being built and not only of one day.

Four things in the figure are deliberately not blue, because they are not part of what was measured. They are drawn anyway so the picture is of the intended system:

  • Slack and Teams — further control surfaces onto the same harness, so a request can start from where people already talk. Planned; neither is connected today.
  • SAKE — the FastAPI service being built for Omics-Studio. Today the harness calls the model directly. The intention is that SAKE takes over that call, so that model access has one owner rather than one per client. Nothing in this prototype depends on that move.
  • B-Fabric via bfabricPy — B-Fabric is FGCZ's order and sample database; bfabricPy is its Python client. The tool server has no B-Fabric tool at all today, which is why order metadata cannot yet be read on this path — and reading it is the whole point of the finished system.
  • Bash — shell commands on the host machine. This one is amber rather than grey, and the difference is real: the capability is switched on in the harness configuration and unsandboxed, it has simply never been exercised. It is the “1 capability enabled but not yet measured” counted at the top of this report.

2Two routes, one user interface

The Web UI can send a turn by either of two routes, chosen from a dropdown. This matters because the two are not equivalent in cost, and pretending otherwise would mislead whoever operates the system.

Why the slower route is the default

The harness is the part of OMAKASE that is meant to grow: sessions, memory, scheduling and delegation all live there. If simple tasks quietly bypassed it, the prototype would prove only that the fast path works, and every later feature would be built on an untested foundation. So the default sends everything through the harness, and the direct route stays available for when speed matters.

4The safety model

The chain can start real compute and write to a database, so it is worth being explicit about what stops it doing that in the wrong place. There are five independent gates. They were tested by trying to get past each one.

A defect this work uncovered, worth repeating because it is a general trap

The UI had been reachable from the whole network for two days without anyone intending it. The cause was a configuration line that read as unset — an environment variable present but empty. The code asked for “this value, or the safe default”, and an empty value is still a value, so the safe default never applied and the server bound to every network interface. It now treats empty as unset. Any configuration reader in this project should be checked for the same mistake.

One confusing thing about this test node, which is not a fault in the chain

fgcz-h-083 runs two copies of the background job daemon, so every job is submitted to the cluster two or three times. Exactly one copy succeeds; the others stop because the output folder already exists. A job row can therefore say failed while its results are complete and correct. Judge a run by the cluster accounting record and by the output folder, never by the row alone. This is a known condition of the test node and does not exist in production.

6How to operate it

Both long-running pieces are held in detached terminal sessions, so they survive the person who started them logging out. Neither is a system service yet; that is deliberate for a prototype. 

# Start or restart the harness
screen -S hermes-gateway -X quit
screen -dmS hermes-gateway -L -Logfile /tmp/hermes_gateway_8642.screenlog \
       bash /srv/sushi/kairos_agent_server_dev/run_hermes_gateway.sh

# Start or restart the Web UI
screen -S kairos-agent -X quit
cd /srv/sushi/kairos_agent_server_dev
screen -dmS kairos-agent -L -Logfile /tmp/kairos_agent_8770.screenlog bash run.sh

# Is everything healthy? Reports both routes and the tool server in one call.
curl -H "Authorization: Bearer $UI_TOKEN" http://127.0.0.1:8770/api/health

7The use case that comes next

A meeting on 2026-09-10 fixed the next target. None of this section is implemented. It is written down here so that the shape of the work is visible before anyone plans it, and because two questions have to be answered before the rest can even be estimated.

The sequence starts with something that already happens every day. When quality control for an order is finished, a member of staff opens B-Fabric — the FGCZ database that holds orders and samples — and sets that order's status to processed. Today nothing downstream reacts to that. The use case is that OMAKASE reacts to it.

What is actually new here

The existing SUSHI runs one App at a time, chosen and launched by a person who then waits, looks at the result and launches the next one. What the meeting asked for is a chain of Apps proposed as a single unit and then carried to the end by the system. That combination step is the capability the existing SUSHI never had, and it is the reason this is worth building rather than scripting.

Two of the boxes in that example carry a judgement rather than a fixed setting, and they are the interesting ones. STARApp needs a reference genome, which has to be derived from the order metadata rather than typed in. EdgeRApp needs to know which samples are the controls and which are the ones being tested — today a person decides that by reading the sample names and the order description, and the system would have to propose it and be corrected when it is wrong.

The two questions that come before any plan

Question 1 — how does OMAKASE learn that an order became processed?

Two shapes are possible. Pull: OMAKASE asks B-Fabric on a timer, using bfabricPy, the Python client for that database. Push: something added on the B-Fabric side tells OMAKASE when the status changes. Pull is entirely within our control; push is cheaper to run but depends on what B-Fabric allows us to add. Neither has been investigated. The specific unknown for pull is whether the order status is among the fields bfabricPy actually exposes.

Question 2 — how does OMAKASE know whether a job finished, and finished correctly?

Watching every job continuously does not scale, so the choice is between being told when a job ends and asking periodically. Two complications are already known. First, SUSHI Apps run in two modes — one job per sample, or one job for the whole dataset — so the unit whose success has to be judged is not the same in both. Second, and measured in this very report: on the test node each job is submitted two or three times by a duplicated daemon, exactly one of which completes, so reading the job's status alone gives the wrong answer. Whatever is built has to judge from the results on disk, not only from a status field.

One thing this use case does not change: the always-running part that watches for finished orders and moves the chain forward stays plain, ordinary code. The model proposes and explains; it does not hold the timer or the state machine. That is the same design decision recorded at the end of the next section, and this use case was designed to respect it.

One design decision that this work respects and should keep respecting

The always-running part of the future system stays plain, ordinary code. Triggers, timers and state machines are not given to an agent, because then the order in which things happen would depend on a model's judgement and the system could no longer be said to be reproducible. The harness introduced here is the control and conversation layer only. It holds no timer and no state machine, and that separation is what keeps the earlier design decision intact.

9Summary

A person can now type a request in a browser, or ask from Claude Code, and a real analysis job starts on the cluster, having passed through an agent harness, an on-premises model, a hundred-tool action server and the production REST API. Four jobs prove it, three different entry points give byte-identical scientific output, five independent gates stand between a request and a database write, and the live production database was not touched once.

What remains is not plumbing. It is the analysis logic itself — which finished orders deserve attention, and which recipe each one should get — and that needs domain expertise rather than more engineering.

Section 7 turns that into a concrete target: an order marked processed in B-Fabric leads to a chain of existing SUSHI Apps being proposed to a bioinformatician, and, once approved, being carried to the end by the system. Proposing and managing a chain rather than a single App is the capability the existing SUSHI never had, and it is what makes this worth building. Before any of it can be planned, two questions need answers: how OMAKASE learns that an order became processed, and how it learns whether a job finished correctly. Neither has been investigated yet.
