1チェーンの構成

人間と計算ジョブの間には、現時点で 5 つの構成要素があります。いずれも本プロトタイプより前から、 それぞれの理由で存在していたものです。2026-09-09 の作業は、それらを 1 本の経路にまとめ、実測する ことでした。図には、この実測に含まれない部分も灰色と橙色で描いてあります。1 日の作業結果 ではなく、これから作るシステムの姿として読めるようにするためです。

図の中で青以外の色にしてある要素が 4 つあります。実測に含まれていないという意味です。 それでも描いてあるのは、これから作るシステムの姿を示すためです。

  • Slack と Teams — 同じハーネスに対する追加の操作面です。人がすでに会話している場所から 依頼を出せるようにする狙いですが、実装予定で、現在はどちらも接続されていません。
  • SAKE — Omics-Studio 向けに構築中の FastAPI サービスです。現在はハーネスがモデルを直接 呼んでいますが、将来はこの呼び出しを SAKE に委譲します。そうするとモデルへの入口が クライアントごとに増えず、1 か所に集約されます。本プロトタイプはこの移行に依存していません。
  • B-Fabric(bfabricPy 経由) — B-Fabric は FGCZ のオーダーと検体の情報を持つデータベース、 bfabricPy はその Python クライアントです。ツールサーバには現在 B-Fabric 用のツールが 1 つも ありません。つまりこの経路ではまだオーダーのメタデータを読めず、それを読むことこそが完成形の OMAKASE の目的です。
  • Bash — ホスト上の Linux コマンド実行です。ここだけ灰色ではなく橙色にしてあり、この違いは 実質的です。この機能はハーネスの設定ですでに有効で、サンドボックスもかかっていません。 ただ一度も実行していないだけです。本レポート冒頭の「有効だが未実測の機能 1 件」がこれです。

7次に実現するユースケース

2026-09-10 のミーティングで次の目標が決まりました。この節の内容はいずれも未実装です。 計画を立てる前に作業の形を見えるようにするため、そして残りを見積もる前に答えを出さなければ ならない問いが 2 つあるため、ここに書き留めます。

出発点は、すでに毎日起きている出来事です。あるオーダーの品質確認が終わると、担当者が B-Fabric ——オーダーと検体の情報を持つ FGCZ のデータベース——を開き、そのオーダーの状態を processed に変更します。現在、この変更に反応するものは何もありません。 これに OMAKASE が反応する、というのが今回のユースケースです。

問い 2

ここで本当に新しいのは何か

既存の SUSHI はアプリを 1 つずつ実行します。人が選んで起動し、待って、結果を見て、次を 起動します。今回のミーティングで求められたのは、アプリの連鎖を一つのまとまりとして提案し、 システムが最後まで運ぶことです。この組み合わせの段階こそ既存の SUSHI が持たなかった能力で、 スクリプトを書くのではなく作る価値がある理由です。

この例の中で、固定の設定ではなく判断を含む箱が 2 つあり、そこが要点です。STARApp は参照ゲノムを必要としますが、これは人が入力するのではなく、オーダーのメタ情報から導かなければ なりません。EdgeRApp はどの検体が対照群でどれが比較対象かを知る必要があります。現在は 人が検体名とオーダーの記述を読んで決めており、システムはそれを提案し、外れていれば訂正を受ける という形になります。

計画より先に答えるべき 2 つの問い

問い 1 — オーダーが processed になったことを、OMAKASE はどうやって知るのか

形は 2 通りあります。取りに行く方式：そのデータベースの Python クライアントである bfabricPy を使い、OMAKASE が一定間隔で B-Fabric に尋ねます。通知を受ける方式： B-Fabric 側に何かを追加し、状態が変わったときに OMAKASE へ伝えてもらいます。前者は完全に こちらの制御下にあり、後者は運用が軽い代わりに B-Fabric 側で何を追加できるかに依存します。 どちらも未調査です。前者について具体的に分かっていないのは、オーダーの状態が bfabricPy から実際に読める項目に含まれているのかという点です。

問い 2 — ジョブが終わったこと、しかも正しく終わったことを、どうやって知るのか

全ジョブを常時監視するのは規模的に無理なので、終了時に知らせてもらうか、定期的に尋ねるかの 選択になります。すでに分かっている厄介な点が 2 つあります。第一に、SUSHI アプリには検体ごとに 1 ジョブを出す方式とデータセット全体で 1 ジョブを出す方式があり、成功を判定する単位が同じでは ありません。第二に、これは本レポート内で実測した事実ですが、テストノードでは常駐プロセスの 二重起動により各ジョブが 2〜3 回投入され、そのうち 1 つだけが完了します。つまり ジョブの状態欄だけを読むと誤った答えが出ます。作るものは、状態欄だけでなく ディスク上の結果から判定できなければなりません。

このユースケースが変えない点が 1 つあります。完了オーダーを監視し連鎖を前に進める常時稼働 部分は、普通のコードのままにします。モデルは提案と説明を担当し、タイマーや状態遷移は持ちません。 これは次節の末尾に記した設計判断と同じもので、本ユースケースはそれを守るように組み立ててあります。

将来のシステムの常時稼働部分は、素朴な普通のコードのままにします。トリガ、タイマー、状態機械は エージェントに持たせません。持たせると、物事が起きる順序がモデルの判断に依存し、システムが 再現可能だと言えなくなるからです。ここで導入したハーネスは制御と対話の層だけです。タイマーも 状態機械も持っておらず、その分離が既存の設計判断を保っています。

9まとめ

人がブラウザで依頼を打ち、あるいは Claude Code から頼むと、エージェントハーネス、オンプレのモデル、 100 個のツールを持つ実行サーバ、そして本番の REST API を通って、計算クラスタ上で実際の解析ジョブが 始まります。4 件のジョブがそれを証明し、3 つの異なる入口が科学的にバイト一致する出力を与え、依頼と データベース書き込みの間には独立した 5 つの関門が立ち、稼働中の本番データベースは一度も触られて いません。

残っているのは配管ではありません。解析ロジックそのもの——どの完了オーダに注意を払うべきか、 それぞれにどのレシピを当てるか——であり、それにはさらなるエンジニアリングではなく領域知識が 必要です。

第 7 節は、それを具体的な目標に落としたものです。B-Fabric 上でオーダーが processed に なったら、既存の SUSHI アプリの連鎖がバイオインフォマティシャンに提案され、承認された後は システムが最後まで運ぶ。単体のアプリではなく連鎖を提案し管理することこそ、既存の SUSHI が 持たなかった能力であり、これを作る価値の中身です。着手を計画する前に答えるべき問いが 2 つ あります。オーダーが processed になったことをどう知るか、そしてジョブが正しく 終わったかどうかをどう知るか。どちらもまだ調査していません。
